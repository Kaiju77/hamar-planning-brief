\begin{abstract}
Our project turns selected text from a Hamar planning notice into a short Norwegian
draft. It shows what is proposed, where, the deadline, and how residents can take
part. A local model extracts facts and quotes. Python formats the draft and checks
it before saving. Five runs on a 21-word extract passed the checks. Five more runs
on a longer extract also passed, but missed important information. This shows that
passing the checks does not mean the draft is complete. We describe the current
program, its limits, and what we plan to improve before the exam. Students still
need to review and edit this draft.
\end{abstract}

\section{Problem and what counts as success}
We chose a local problem: making a planning notice easier to read. Our intended
user is a Hamar resident who wants to know what might change and how to give input.
The example is a planned cycleway with a pavement along Ringgata, between
Solvangvegen and Disenvegen \citep{hamar}. Norwegian output and a local source
connect the project to Innlandet. We have not interviewed residents, so the need
is still an assumption rather than something we have measured.

We limit the project to official planning notices that invite public input.
Unrelated news, grants and finished decisions are outside this scope. A person
chooses the text before the program runs. It is not a website crawler. The program
should return either a draft with evidence or a clear failure report.

The first input has 21 words in three separate passages. It includes the proposal,
location, planning stage and deadline. It leaves out participation and the response
route. The full page does contain these details. A second, 61-word input adds the
institutional mailbox, postal address, case number and open office day. Both inputs
are selected passages, not full notices. They contain no individual names or
personal contact details. The page was fetched again on 29 October, and the new
passages were checked against that response. Student source review is still pending.
No general permission to crawl or redistribute the site has been established.

\textbf{Success for the first input} means finding the cycleway and pavement, both
street endpoints, the start of planning work, and the deadline of 18 November
2026. The two omitted fields should be \texttt{unknown}. For the longer input,
the draft should also show the office day under participation and put the official
submission details in the response-route field. Our prompt does not yet ask for exactly
this split (see Section 3). Both drafts must link to the source, show a check
date and say \texttt{needs\_human\_review}. Passing the code checks is a separate,
weaker result. It does not prove that the draft meets all these goals.

\section{How the program works}
Repository: \url{https://github.com/Kaiju77/hamar-planning-brief}.
It contains the code, context prompt, inputs, saved runs, tests and instructions.
The program uses Python's standard library and the local Ollama API \citep{ollama}.
One command runs four stages without a person moving data between them.

\paragraph{1. Load the selected text.}
\texttt{run.py} reads a text file and a metadata file with the source URL, retrieval
date and partial-source flag. Input is limited to 12,000 characters. The model
receives the extraction prompt and the text inside source markers. It cannot
fetch the URL itself. It does not receive our chat history, other notices,
credentials or access to files. A person must choose and screen the input.

\paragraph{2. Ask the model for facts.}
The model returns a scope decision and six fields: proposal, location, planning
stage, deadline, participation and response route. Each field has a value and a
supporting quote. The prompt says to use \texttt{unknown} or \texttt{ambiguous}
instead of guessing. It also says that source text is data, not instructions.
The model is \texttt{qwen2.5-coder:7b}, with temperature zero and JSON output.
A deadline should become an ISO date only when day, month and year are explicit.
An official mailbox is allowed; an individual person's contact details are not.

\paragraph{3. Make the Norwegian draft.}
Python places the facts in a fixed template. It starts with the proposal, location,
deadline, participation and response route. The planning stage, evidence and source
follow. This uses no second model call. The earlier plan had a model for drafting
too. A template is simpler and cannot add new facts by itself, but it also does
little to improve the model's wording. Missing information stays visible.

\paragraph{4. Check and save.}
\texttt{checks.py} checks field types, source metadata, evidence and the deadline.
Quotes must occur in the input, ignoring case and repeated spaces. The normalized
deadline must match a Norwegian date in its own quote. Code compares the deadline
with the recorded Oslo check date. A date-only deadline stays open through that
day. An unknown or ambiguous deadline has unknown status. Exact cutoff times are
not handled yet. If a check fails, the program saves errors and no draft.
If checks pass, it saves JSON and Markdown. A quote occurring in the input does
not prove that it supports the value beside it.

\paragraph{Tools, automation and limits.}
Python reads and writes files, calls the local HTTP service and runs the checks.
The model cannot run commands or publish anything. Each attempt has its own folder
with the raw response, extracted facts, time, token counts and an input/prompt
snapshot. There is one model call, no automatic retry, an 800-token output cap and
a 120-second HTTP timeout. These limits are not yet a measured total token budget.
Ctrl+C stops the client, but the model server may also need \texttt{ollama stop}.
Python still has the user's normal file permissions. Stronger path restrictions,
budgets and a clear halt policy are work for the exam.

\ExtendedFindings
The reference checks look for selected words, dates and addresses. They are not
a full test of meaning or good Norwegian. Timing is also not a controlled speed
comparison: loading the model can make the first run slower. Temperature zero
does not guarantee the same answer on another machine or model version.

Earlier attempts are kept separately. One \texttt{llama3.2:3b} response rejected
the notice as outside the scope and returned invented quotes and a non-ISO date.
It produced a failure report. Scope rejection stops later checks, so this does
not show that every invented quote was detected. Five earlier Qwen runs used an
older field contract and are not added to the table.

Twelve unit tests pass. Seven cover the original synthetic cases: a normal case,
missing and ambiguous dates, wrong scope, altered evidence and two injection
outcomes. Five more cover malformed deadlines, date boundaries, missing files,
separate output folders and an unavailable Ollama service. Fixture evaluation
uses canned model replies. It tests program behaviour, not a live model's ability
to resist an attack.

One known injection case still saves an unsafe draft. If the model follows an
instruction in the source and quotes the injected date, the evidence check can
pass. A warning is not enough to stop it. A made-up location or personal contact
detail paired with a genuine quote can also pass because non-date values are not
checked for meaning. We have not tested many notices, conflicting deadlines or
resident usability. A person still needs to compare the draft with the source.

For the exam, the two planned failure classes are changed input and dependency
failure. The first will include misleading instructions and conflicting facts in
synthetic notices. The second will include a refused connection, timeout and bad
model JSON. We will save what happened, repair the relevant stage and rerun the
same cases plus the other tests. This is planned work, not completed security
testing. We also need a broader set of normal, missing, conflicting and out-of-scope
inputs. Code can check format and dates; people must assess meaning and clarity.
A proposed halt rule is to stop after three invalid runs and ask for review.
That rule is not implemented yet. Demo feedback and later repairs will go in the
final paper, together with the actual meeting records.

\section{Reproduction and one saved evaluation}
Install Python 3.10+ and Ollama and pull \texttt{qwen2.5-coder:7b}. No Python
packages are needed. From the project folder:
\begin{lstlisting}
python -m unittest discover -s tests -v
python evaluate.py --backend fixture
python evaluate.py --backend ollama --count 5 --example ringgata_extended --checked-at 2026-10-29
python tools/build_results.py
\end{lstlisting}
The fixed date reproduces this check. For a new operational run, pass the actual
Oslo date. Fixture replies are canned. The results builder uses fixed saved batches.
The raw evaluation summary below keeps the original values. In it, \texttt{matches\_fixture\_behavior\_expectation} only says the code behaved as the fixture rules expect. It does not say the content was complete: all five drafts there still lack the office day and route. Individual raw model
replies and input snapshots are in the referenced folder.
